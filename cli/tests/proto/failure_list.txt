# Tests the Buri implementation is expected to fail, and why.
#
# Recorded from a run and then grouped: every entry belongs to one of the seven
# reasons below, and each reason is a decision written down somewhere else -- in
# README.md for what was removed from the vendored schema and what edition it
# was migrated to, in `buri docs build/proto` for the mapping, in `core/proto`
# for the wire format.
#
# **Nothing here is an unexplained failure.** The runner fails if a listed test
# passes, so this file cannot rot in the direction of hiding a fix; and a test
# that starts failing has to be classified before it can be added.
#
# The reference implementation is proto3 and the schema under test is edition
# 2026, so one group below is not a gap at all: it is the two schemas disagreeing
# about presence, correctly, in the way editions changed.
#
# Counts when this was recorded: 970 succeeded, 1314 skipped, 456 expected to
# fail, 0 unexpected. `./run.sh --update` rewrites the names, and leaves the
# grouping to whoever reads the diff.

# --- `map<K, V>`, refused by the schema reader --------------------------------
#
# A map field is sugar for a repeated entry message with a wire layout of its
# own, and Buri's `Map` is not ordered the way a decoded one would have to be.
# Every map field was deleted from the vendored schema, so a test that sets one
# round-trips to nothing. Declaring the entry message explicitly is the
# supported way to say the same thing.
# (258 tests)

# --- Explicit presence, which is the edition's default and not proto3's --------
#
# The one entry here that is a *behaviour difference* rather than a gap. The
# vendored schema was migrated to edition 2026 and takes the edition's own
# defaults, so `features.field_presence` is EXPLICIT: a field the input set is a
# field the output writes, at its zero value as much as at any other. The
# reference message is proto3, where a singular scalar has no presence and a
# zero is indistinguishable from an absent field -- so it expects
# `{"FieldName13": 0}` in to produce `{}` out, and gets `{"FieldName13":0}`.
#
# Both are right about their own schema. The reader implements editions, and
# this is what editions says. `buri docs build/proto` states it under "Presence
# is the headline". The same difference shows up in the binary direction as
# ~18 `Recommended` warnings, which do not fail the suite.
# (1 tests)
Required.Proto3.JsonInput.SkipsDefaultPrimitive.Validator

# --- Unknown fields are dropped rather than retained --------------------------
#
# Decoding skips a field the schema does not know, which is the forward
# compatibility every edition has; it does not *keep* the bytes, because a
# generated struct has nowhere to put them. A message decoded from a newer
# schema and re-encoded therefore loses what that schema added. Stated in
# `core/proto`.
#
# Unrecognised *enum values* are no longer in this group: editions enums are
# open, and the generated enum keeps one in an `Unrecognized` variant.
# (2 tests)
