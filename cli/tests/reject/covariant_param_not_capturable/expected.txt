     What to do
     ──────────

     Take it as a parameter of the lambda instead — the fn(C, A) => B shape a
     *Ctx combinator passes — or return the value rather than a closure over it.

     The rule
     ────────

     lambda-captures-effect is the same rule where the type says so out loud.
     Here the type does not say so, and cannot. Inside fn hide<T>(x: T), T is
     opaque, and the compiler checks a generic body once for every instantiation
     at once rather than once per call site. If the rule asked only "does this
     type mention an effect?", the answer for T would be no. hide(ctx) would be
     well-typed at the call site, and the closure that came back would hold a
     capability behind a type that mentions none. Stopping exactly that is the
     point of the capture rule, so the rule stays conservative here.

     A type parameter escapes the restriction when it carries an ordinary trait
     bound. A type is either part of the world or part of your data, never both,
     so a T: Eq can never be instantiated at a context type. That is why
     xs.any(fn(x) => x == needle) is still legal inside impl<T: Eq> [T].

     Function types escape it too, for a different reason: a closure holds
     exactly what it captured, and this rule is what checks that. So fn
     compose<A, B, C>(f: fn(A) => B, g: fn(B) => C): fn(A) => C { fn(x) =>
     g(f(x)) } is fine.
