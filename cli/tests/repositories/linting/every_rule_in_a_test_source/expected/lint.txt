warning: this spells the milliseconds to nanoseconds conversion out in integers [time-unit-conversion]
  --> lib/money/test/cents.buri:19:5
   |
19 | let NANOSECONDS_PER_MILLISECOND: I64 = 1_000_000;
   |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^
   |
   = `core/time`'s `Duration` is the length itself — `time.milliseconds(n)`, `time.seconds(n)` — and its arithmetic saturates, so a deadline built from one cannot overflow into the past
   = fix: build a `Duration` and let the unit live in the type rather than in the name

     An I64 of milliseconds carries its unit only in its name, and every
     conversion is a hand-written multiply that can drop, double or overflow the
     unit unnoticed:

       let IDLE_TIMEOUT_MILLIS: I64 = 30_000;

       fn deadlineNanos(startedNanos: I64): I64 {
           startedNanos + IDLE_TIMEOUT_MILLIS * 1_000_000
       }

     Use core/time instead:

       from "core/time" import * as time;
       from "core/time" import { Instant };

       fn expired(started: Instant, now: Instant): Bool {
           now.hasPassed(started.plus(time.minutes(5)))
       }

     - Constructors: seconds, milliseconds, microseconds, nanoseconds,
     minutes, hours.

     - Arithmetic: add, subtract, multiply, negate, abs.
     - Readers: nanoseconds(), milliseconds() and the rest, in any unit.

     You never need a conversion factor. Two things come with the type:

     - The arithmetic saturates. An oversized length becomes the largest length,
     not a negative one, so a deadline can't overflow into the past.

     - The unit is in the type. Duration and Instant differ on purpose: a
     length plus a point is a point, two points make a length, and adding two
     points is a type error.

     The rule fires on constants named as conversions, like
     NANOSECONDS_PER_MILLISECOND or MILLISECONDS_PER_SECOND, and on a
     millisecond count multiplied by a million in place. A million not named as
     milliseconds is left alone, since parts per million is a real thing.

  --> lib/money/test/cents.buri:35:4

     Parameters that travel together across calls are a missing abstraction. To
     find it:

     - Look at the call sites and nearby functions for a type a group of these
     parameters already belongs to. Values that keep appearing side by side are
     usually one of the domain's nouns.

     - If there's none, create it, and move the behaviour that uses those fields onto

     after its function is the same bag, so the next function invents another
     and the concept stays unnamed. You're done when the type has a domain name
     and no call site passes its fields loose.

  --> lib/money/test/cents.buri:39:4

   = fix: call `order.int` with the two operands, and delete the chain

           if (left < right) { .Less } else if (left > right) { .Greater } else { .Equal }

     That function is order.int, character for character. Hand-written

warning: `ctx` is not used; the function is pure [unused-context]
  --> lib/money/test/cents.buri:43:24
   |
43 | fn width<C: Allocator>(ctx: C, label: Str): Int {
   |                        ^^^^^^
   |
   = a `ctx` parameter is the whole of what a function may do to the world, so one the body never reads makes every caller hold a context for a computation that touches nothing
   = fix: remove the `ctx` parameter, and the context argument at every call site

     ctx is where a signature says what a function may do to the world. A
     function that takes one and never reads it makes every caller pass a
     context, so a pure computation drags the ability to write files up through
     everything that reaches it.

     A body uses a context by handing it to a callee that asks for one, like
     io.println(ctx, x), or to a function-typed parameter. Both name ctx, so the
     rule asks one question: does anything in the body name ctx?

     What is not asked
     ─────────────────

     - A method supplied by an `impl`. The signature is the trait's, and an
     implementation can't drop a parameter.

     - A function with no body: a trait method's signature, an effect's
     operation, a standard library intrinsic.

     - A lambda. A lambda can't capture a context (lambda-captures-effect), so
     one that needs a context takes it as its own parameter.

     The fix
     ───────

     Delete the parameter, and the argument at every call site. buri lint --fix
     and the editor quick fix make that edit, except when:

     - the name is on the library's surface. lib.buri publishes it, so callers
     may live in packages this analysis never loaded. Decide whether the
     signature is part of your published API first.

     - something takes the function as a value. Where a fn(C, ...) is
     expected, deleting the parameter makes it the wrong type.

     - the package did not type-check. The list of call sites may be incomplete.
     The finding still stands, because the rule falls back to looking for ctx in
     the text.

     Which effects the context carries is unused-context-bound's question. This
     rule only reports a context the body never names.

warning: bound `Allocator` on `C` is not used by this function [unused-context-bound]
  --> lib/money/test/cents.buri:47:16
   |
47 | fn announce<C: Allocator + Stdout>(ctx: C, label: Str): Result<(), IoError> {
   |                ^^^^^^^^^
   |
   = a bound on a context parameter is a demand made of every caller — it says the function needs that capability, and one the body never exercises makes callers hold a capability for nothing
   = fix: remove the bound

     A ctx parameter's bounds say which parts of the world a function touches.
     fn save<C: Allocator + FileSystemWrite>(ctx: C, …) allocates and writes
     files, and every caller must hold a context that can do both. A dead bound
     spreads, because each caller's signature has to carry it too.

     A body uses a bound in exactly two ways, both calls:

     - A callee that asks for it. io.println(ctx, x) makes its own bounds
     demands on C, so the bounds it names are used and the rest are not. This is
     the only way an effect gets used: you call an effect through the module
     that wraps it, not on the context (SPEC 10.2).

     - A function-typed parameter. render(ctx, label), where
     render: fn(C, Str) => Str, hands the whole context to unseen code, so it
     uses every bound.

     What is not asked
     ─────────────────

     - A method supplied by an `impl`. Its bounds must match the trait's, so a
     dead bound there is dead on the trait.

     - A function with no body: a trait method's signature, an effect's
     operation, a standard library intrinsic.

     - A parameter that is not a context. The rule only looks at a ctx
     parameter's type parameter, and only when at least one bound is an effect.

     - A body that did not type-check. Without the typed tree, the rule can't
     see which callee uses which bound, so it says nothing.

     The fix
     ───────

     Delete the bound. Unlike a ctx parameter, a bound touches no call site, so
     the fix is offered even when the name is on the library's surface.

     Removing FileSystemWrite and Io from <C: Allocator + FileSystemWrite + Io>
     is one rewrite, because the bounds share their + separators. Every finding
     on one parameter carries the same rewrite, buri lint --fix applies it once,
     and the next run is clean.

     The fix is withheld when anything but separators sits between the bounds,
     so a comment inside a bound list never gets deleted.

     this rule puts every such call in one report.

           io.println(ctx, line).ignore()

     other. A program that cares matches on the print, as buri init's template
     does.

     warning stand is fine. The point is that somebody decided.

warning: this branch is nested 5 levels deep [deep-nesting]
  --> lib/money/test/cents.buri:67:21
   |
67 |                     if (n > 10000) { "huge" } else { "large" }
   |                     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
   |
   = the limit is 4; an `else if` chain counts as one level, and a lambda body starts again at zero
   = fix: pull the inner branch into a named function, or replace the ladder with one `match`

     Deep nesting makes you hold every condition in your head at once. The
     problem isn't the indentation; it's a function that branches too much in
     one place.

     Read from the inside out and ask what the innermost block needs. Most
     enclosing conditions are guards to check and bail on, not to wrap the real
     work. Prefer, in order:

     1. Guard clauses. Invert a condition and return early. Each one lifts
     everything below it a level. 2. Replace the structure. A deep if/else
     ladder is often a lookup table, or an enum and a match. 3. Extract a
     helper. Pull a coherent inner step into a named function.

     Don't merge conditions with && just to drop a level; that trades nesting
     for an unreadable condition. When the algorithm really is deep, still keep
     each function shallow by extracting inner loops into well-named helpers.
