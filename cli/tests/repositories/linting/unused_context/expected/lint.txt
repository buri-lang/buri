   = fix: remove the `ctx` parameter, and the context argument at every call site

     ctx is the one place a Buri signature says what a function may do to the
     world. A function that declares one and never reads it says yes and means
     no, and the cost lands on the callers: a pure computation drags the ability
     to write files up through every function that reaches it.

     The body is the whole of the evidence. There are exactly two ways to use a
     context: hand it to a callee that asks for one, or hand it to a
     function-typed parameter. Both read the parameter, so the rule asks one
     question — does anything in the body name ctx?

     Calling an effect's operation is the first of those two, not a third way of
     its own. You perform an effect by handing the context to a function (SPEC
     10.2), so io.println(ctx, x) is a callee that asks for one.

     What is not asked
     ─────────────────

     A method supplied by an `impl` is not asked. The signature is the trait's,
     and an implementation cannot drop a parameter the trait declared.

     A function with no body is not asked. A trait method's signature, an
     effect's operation and the standard library's intrinsic declarations
     describe what an implementation will be handed. There is no body to read.

     A lambda is not asked. A lambda may not capture an effect-carrying value at
     all (lambda-captures-effect), so a ctx parameter is never inside a
     closure's environment. A lambda that *is* handed a context takes it as a
     parameter of its own.

     The fix, and when it comes as bytes
     ───────────────────────────────────

     Delete the parameter, and the argument at every call site. buri lint --fix
     and an editor's quick fix apply that same edit when they can see the whole
     of it. They decline, and leave you the sentence, in three cases:

     * the name is on the library's surface. lib.buri publishes it, so a call
     site may be in a package this analysis has never loaded. Decide whether the
     signature is part of what you publish before changing it.

     * something takes the function as a value. A function passed where a
     fn(C, ...) is expected has the shape that type demands rather than the one
     its body needs, so deleting the parameter would make it the wrong type.

     * the package did not check whole. The list of call sites is short by an
     unknown amount. The finding itself still stands: where the typed tree is
     truncated this rule reads the text instead, and a context has one spelling,
     so "does this declaration write ctx anywhere but at the parameter" is a
     question the lexer can still answer.

     None of this is about *which* effects the context carries. That is
     unused-context-bound's question. This one is only about a context nothing
     in the body names at all.
